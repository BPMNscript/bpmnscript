# @bpmn-script/language

The Langium language package for BPMNscript. Provides the grammar, parser, AST, validator, and language server used by the VS Code extension and the CLI.

## In plain terms

This package knows the BPMNscript _language_ itself: what counts as valid syntax, and how to turn source text into a structured tree the rest of the toolchain can work with.

You write the language's rules once, in a single grammar file (`src/bpmn-script.langium`). [Langium](https://langium.org/) reads that grammar and generates three things for you: a **parser** (text → tree), the **AST** types (the tree's shape, as TypeScript interfaces), and a **language server** that powers the in-editor experience — syntax highlighting, autocompletion, and the red squiggles under mistakes. None of that generated code is checked in; `npm run build` regenerates it from the grammar.

The only logic written by hand on top of Langium is the **validator** (`src/bpmn-script-validator.ts`): the structural rules a parser alone can't express, such as "a service task needs exactly one binding attribute (`class`, `expression`, or `delegate`)" or "a variable reference must match a declared `var` type." Langium already reports purely syntactic errors and unresolved references; the validator adds the BPMN-specific and type-system rules.

## Purpose

This package contains everything Langium generates and everything written on top of it:

- The BPMNscript grammar (`src/bpmn-script.langium`) covering the supported BPMN subset.
- The structural validator (`src/bpmn-script-validator.ts`) for AST-level BPMN constraints.
- The Langium-generated parser, AST types, and language server module (built artifacts in `out/`; source in `src/generated/` — both git-ignored, regenerated by `npm run build`).
- The base VS Code TextMate grammar (`syntaxes/bpmn-script.tmLanguage.json`, git-ignored, generated by `langium generate`). A separate hand-maintained injection grammar in `packages/extension` layers embedded-language highlighting onto a `script` task's fenced body on top of this base grammar — see [`packages/extension/README.md`](../extension/README.md).

## Grammar overview

The grammar accepts files with one `process` block per file. Sequence flow is implicit (top-to-bottom); control flow is expressed with structured statements. Optional `var` declarations go in the process header before the body.

```bpmnscript
process invoice-approval {
  var amount: number

  start ReviewStart
  user ReviewInvoice { assignee = "demo" }
  if (amount > 1000) {
    user SeniorApproval { assignee = "manager" }
  } else {
    service AutoApprove { class = "com.example.AutoApproveDelegate" }
  }
  end Done
}
```

Supported statements: `start`, `end`, `user` (attribute block: `assignee`, `formKey`), `service` (attribute block: exactly one of `class`, `expression`, or `delegate` — `class` is a Java delegate class name, `expression` maps to `operaton:expression`, `delegate` is a friendly alias for `operaton:delegateExpression`), `external` (attribute block: `topic`, delegates to an external worker via `operaton:type="external"` + `operaton:topic`), `script` (a markdown-style fenced body opened by a language tag, e.g. ` ```js … ``` `, mapping to `bpmn:scriptTask`; supported tags are `javascript`/`js`, `groovy`, `python`/`py`, `ruby`/`rb`, and `feel`), `if`/`else if`/`else`, `while (cond) { }`, `do { } while (cond)`, `parallel { { } { } }`, `goto <id>`, `subprocess <id> "<label>"? { }` (a nested flow container mapping to `bpmn:subProcess`; its body is a plain statement block using the same construct vocabulary as a process body — including a nested `subprocess` — and renders expanded, with its children inside the parent's bounds, in BPMN viewers), `call <id> "<label>"? { }` (starts another process — read like a function call at the process boundary: `process = "<id>"` names the called process, an `in` mapping is an argument passed into it and an `out` mapping is a return value read back from it, `in *`/`out *` copies every variable instead of naming one, `version = <number>` pins a specific deployed version of the called process while `binding = latest`/`binding = deployment` selects the other two version-resolution modes, and `businessKey = "<value>"` sets the started process instance's business key; a `local` mapping — e.g. `in local x = y` — reads from / writes to variables that belong to the call step itself rather than to the whole process, which is rarely needed when authoring and is kept chiefly so diagrams that use step-local variables import faithfully). Every targetable statement carries an explicit `id` (e.g. `user ReviewInvoice`), including `subprocess` and `call` — a sequence flow (or `goto`) may target a sub-process or a call in the same container by its id, the same way it targets any other step. The human-readable BPMN `name` is derived from the id when no label is given (`ReviewInvoice` → "Review Invoice"); an optional quoted label after the id overrides it (e.g. `user ReviewInvoice "Review invoice"`).

### The event layer

The event layer reads like try/catch. An `on <kind> { }` handler is a catch block: it sits at the end of the process or subprocess body it guards, the same way a catch block sits after the try body it belongs to (`on error "PAYMENT_FAILED" { … }`). A parenthesized list right after the code is the caught value — the `e` in `catch (Exception e)` — pairing a binding field (`code`, and for `error` also `message`) with the process variable it fills (`on error "PAYMENT_FAILED" (code c, message m) { … }`); omitting the code (`on error { }`) catches any event of that kind, the catch-all. `alongside` marks a handler non-interrupting: the guarded scope's main flow keeps running beside the handler instead of being interrupted by it. Two verbs raise an event, and the distinction is uniform across every kind: `throw <kind>` ends the current path right there, exactly like `throw` in a programming language, while `emit <kind>` fires the event and keeps going. A process-header declaration, `error "CODE" message "text"`, records the message text a thrown error of that code carries at runtime, written alongside the `var` declarations at the top of the body (needed only for a code whose throw/catch sites should carry that text).

Seven trigger kinds share the `on`/`throw`/`emit` surface:

| Trigger | Payload | `alongside`? | `throw` (ends the path) | `emit` (continues) |
| --- | --- | --- | --- | --- |
| `error` | code + optional `(code c, message m)` catch bindings | no — an error always interrupts | `throw error "CODE"` | — an error has no continuing form |
| `escalation` | code + optional `(code c)` catch binding | yes | `throw escalation "CODE"` | `emit escalation "CODE"` |
| `message` | a name | yes | — arrives from outside; nothing to send | — |
| `signal` | a name | yes | `throw signal "Name"` | `emit signal "Name"` |
| `timer` | a particle (`after`/`at`/`every`) + a time expression | yes | — fires off the clock | — |
| `condition` | a `(condition)` expression | yes | — fires off data | — |
| `compensation` | none | no — its scope has already finished | `throw compensation` | `emit compensation` |

`message`, `timer`, and `condition` are handler-only: nothing in the process raises them, so they have no `throw`/`emit` form. The rest are both caught and raised, all under the one rule above — `throw` ends the path, `emit` continues.

Reading each kind:

- **`error` / `escalation`** — catch blocks. An error always interrupts the scope it guards (BPMN has no non-interrupting error); an escalation may interrupt or, with `alongside`, run beside the main flow, and only ever travels up within its own guarded scope.
- **`message`** — the process's inbox: the handler runs when the engine correlates a message of that name delivered from outside. Correlation is the engine's own mechanism, so the handler needs only the name.
- **`signal`** — a broadcast channel: `emit signal "Name"` notifies every listener anywhere waiting on that name and continues, `throw signal "Name"` broadcasts the same way and ends this path. Broader reach than an escalation.
- **`timer`** — the particle picks the BPMN timer form: `after "PT1H"` a duration, `at "2026-08-01T09:00:00"` a fixed moment, `every "R/PT10M"` a repeating cycle. The clock starts when the guarded scope starts. An interrupting `every` fires only once, since the first firing ends the scope it is timing; add `alongside` to let it keep firing.
- **`condition`** — reads like `if`: the `(expression)` is checked when the guarded scope starts and again whenever a variable it reads changes.
- **`compensation`** — a subprocess's undo block: the steps that reverse whatever the subprocess already finished doing. It runs only when something later throws compensation, and only for a subprocess instance that actually completed. It carries no code, name, condition, or particle of any kind, at most one exists per subprocess, and it sits directly inside the `subprocess` body it undoes — a process has no completed enclosing scope to reverse, so `on compensation` at process level is rejected. `throw compensation` undoes the nearest enclosing scope's completed work newest-first and ends the path; `emit compensation` runs the same undo, waits for it to finish, and continues.

### Attaching a handler to one step (a boundary event)

Every trigger but `compensation` can also name a single host step instead of guarding its whole enclosing body: `on <Host>: <trigger> … { }` attaches the handler directly to `<Host>` as a `bpmn:boundaryEvent`, catching only while that one step is running — `on ReviewInvoice: timer after "PT2H" { … }` reads "if reviewing the invoice takes longer than two hours, do this instead", not "at any point during the whole process". The colon is what tells a host apart from a bare trigger: `on Pack error "X"` and `on timer after "X"` would otherwise both parse as two identifiers followed by a string, since trigger words and timer particles are ordinary identifiers rather than keywords (see below); the colon settles which reading applies before either one is chosen.

`<Host>` has to be a step an engine token can actually be running at: a `user`/`service`/`external`/`script` task, a `subprocess`, or a `call` — never a `start`/`end` event, a `goto`, a `throw`/`emit`, or another handler. `escalation` narrows the legal hosts further, to a `subprocess`, a `call`, or a `user` task, matching Operaton's own restriction on where an escalation boundary may attach. `alongside` keeps its everywhere-else meaning: the host keeps running beside the catch instead of being cancelled the moment the trigger fires; `error` still always cancels its host, exactly as it always interrupts a host-less scope.

A hosted handler's body is self-contained the same way any other `{ }` block is: it ends where its last statement ends and never automatically falls back into whatever follows the host in the main flow — falling through by default would duplicate the token for a non-interrupting (`alongside`) boundary, running the rest of the process twice. Rejoining is always spelled out with a `goto`, which works in both directions: from inside a hosted body back into the main flow, and from the main flow into a step written inside a hosted body, because the body's steps share the host's own container rather than living in one of their own. An explicit `start` cannot open a hosted handler's body, unlike a host-less one — the body has no start of its own, since it is entered from the boundary event rather than from a container's own entry point.

To make a single step undoable rather than a whole subprocess, wrap that step in its own `subprocess` with an `on compensation` block — a small named unit of work with its own undo steps. BPMN can also attach a compensation handler directly to one activity through a boundary event and a separate, otherwise-dormant activity that only runs under compensation; unlike every other trigger kind, `compensation` has no attached form in BPMNscript, and stays the subprocess's own undo block only — the wrap-in-`subprocess` pattern already reaches the same granularity with a construct the language has, and BPMN's boundary-compensation mechanism needs a second, normally-dormant activity this language does not otherwise expose. An undo block sees the subprocess's variables as they stood when it completed — anything changed by whatever ran afterward is invisible to the steps reversing it. Operaton does not carry compensation across the separate process instance a `call` starts, so a called process has to compensate its own work if it needs to. The mental model is the rollback you would write by hand: each unit of work declares how to reverse itself, and when something later fails those reversals replay backwards, newest first, undoing exactly what had already succeeded.

Only `on`, `throw`, `emit`, and `alongside` are reserved keywords for the event layer. `error`/`escalation`/`message`/`signal`/`timer`/`condition`/`compensation` (the trigger kinds), `after`/`at`/`every` (the timer particles), and `code`/`message` (the binding and declaration field names) are deliberately ordinary identifiers, not keywords — `var message: string`, `var timer: number`, and a task named `every` all parse exactly like any other identifier — because they are also among the most common variable and property names a Java-background author reaches for. The editor still highlights and completes them, just only in the positions where they carry event meaning (the first word of `on error`, a timer's particle, a binding field, the declaration), never elsewhere.

Condition expressions are parsed as a real AST (JUEL native subset): integer/decimal/string/boolean/null literals, variable references with dot-property and index accessors, unary `!`/`-`, binary arithmetic and comparison operators, logical `&&`/`||`, ternary `? :`, and parentheses. Expressions outside this subset use the quoted raw fallback `"${…}"`. `on condition (…)` reuses this same expression grammar for its parenthesized condition, so a variable read inside it participates in the same undeclared-variable and type checks as a variable read inside an `if` condition.

## Validator checks

The structural validator in `src/bpmn-script-validator.ts` reports:

- **Warning** — an undeclared variable reference (a `VarRef` whose root identifier has no matching `var` declaration in the enclosing process).
- **Error** — a declared-variable type mismatch (e.g. a `string` variable used under a numeric comparison operator).
- **Error** — a duplicate attribute key in an attribute block (e.g. two `assignee =` entries on one `user` task).
- **Error** — a `service` task with zero, or more than one distinct, binding attribute (`class`, `expression`, `delegate`); exactly one is required.
- **Error** — an `external` task with no `topic` attribute.
- **Error** — a `script` task whose fence language tag is not one of the supported aliases, or whose body is empty.
- **Warning** — a process body with no executable statements.
- **Warning** — an empty `subprocess` body (zero statements) — the same empty-body warning a process gets.
- **Error** — a `process` name reused by a later `process` in the same file.
- **Error** — a `var` name declared twice in one process.
- **Error** — a second `label = "…"` declaration in one process.
- **Error** — a step name (`start`/`end`/`user`/`service`/`external`/`script`/`subprocess`) reused by another step anywhere in the same process — even across a sub-process boundary — which would make `goto` ambiguous; BPMN ids must be document-unique, so this stays a whole-process check regardless of the container-scoped `goto` rule below.
- **Warning** — an empty `if`/`else if`/`else` branch, `while`/`do … while` body, or `parallel` branch (zero statements — syntactically legal, almost always a mistake).
- **Error** — a `goto` that reaches into a `parallel` branch from outside that branch's subtree; a branch's steps only run when the whole `parallel` statement is reached.
- **Error** — an explicit `start` anywhere other than the first statement of its process, subprocess, or host-less event-handler body: later in the same container's statement list, or nested inside an `if`/`while`/`do … while`/`parallel` block at any position, is rejected (a start event cannot have incoming flows). A `start` opening a `subprocess` or a host-less `on` handler body is valid in the same way one opening a `process` body is; inside a host-less handler body, though, the explicit `start` carries the caught event and rejects a `form` block (the trigger start has no form semantics). A _hosted_ handler's body cannot open with an explicit `start` at all — it is not a container of its own, so it is entered by the boundary event rather than by a start of its own.
- **Error** — a `call` with no `process` attribute, or an empty `process = ""`.
- **Error** — a `call`'s `binding` value that is neither `latest` nor `deployment` (with a dedicated message for the common `binding = version` slip, pointing at `version = <number>` instead), or a `call` declaring both `binding` and `version` (they are mutually exclusive version-resolution discriminators).
- **Error** — two `call` mappings naming the same target in the same direction (`in`/`out` are independent), including a second bare `in *`/`out *` in one direction; a `*` alongside a named mapping in the same direction is legal.
- **Error** — an `on`/`throw`/`emit` trigger word outside its legal set (`on` accepts `error`/`escalation`/`message`/`signal`/`timer`/`condition`/`compensation`; `throw` accepts `error`/`escalation`/`signal`/`compensation`; `emit` accepts `escalation`/`signal`/`compensation`), a binding `field` other than `code`/`message`, or an `error … message` declaration whose leading word or field name is wrong — each names the valid word(s) instead of a bare "unknown identifier" complaint; `emit error "…"` is rejected on its own terms, since an error always ends its path, pointing to `throw error` instead, and `throw message`/`emit message` are rejected the same way — a message arrives from outside the process, so there is nothing to send.
- **Error** — a payload that does not match its trigger's shape: `on message`/`on signal` with no name (the engine matches messages and signals by name, so a nameless handler is meaningless); `on timer` with no particle and time, or a bare code string in place of the particle clause; `on condition` with no parenthesized condition; a binding list or a condition expression on a trigger that does not take it (`message`, `signal`, `timer`, and `compensation` carry no bindings; only `condition` takes a condition); a particle word on a non-`timer` trigger; any code, name, or particle written after `on compensation`/`throw compensation`/`emit compensation` at all — compensation has nothing to correlate by, so it takes no payload of any kind.
- **Error** — an `on` handler that does not sit directly in a process, subprocess, or another handler's body — a handler guards a whole container, not a single `if`/`while`/`parallel` branch.
- **Error** — an `on compensation` handler anywhere other than directly inside a `subprocess` body — a compensation event sub-process only exists inside an embedded sub-process, so a process, an `if`/`while`/`parallel` branch, or another handler's body are all rejected as its container; a process cannot compensate itself.
- **Error** — an `on` handler followed by anything other than another handler in the same body — handlers read like catch blocks and belong at the end.
- **Error** — `on error … alongside` or `on compensation … alongside` — an error always interrupts the scope it guards, and a compensation handler's scope has already finished by the time it runs, so there is no main flow left for it to run alongside; `alongside` only makes sense for the other trigger kinds.
- **Error** — an empty code, name, or time string on `on`/`throw`/`emit` (to catch or throw *any* error/escalation, omit the code entirely rather than writing `""`; message, signal, and timer always require their string, so an empty one is rejected rather than treated as absent).
- **Error** — a timer particle other than `after`/`at`/`every`, naming the valid set.
- **Warning** — an `after` time value that looks like neither a duration nor an EL expression, or an `at` value that looks like a duration or cycle instead of a point in time; a repeating (`every`) timer on an interrupting handler, suggesting `alongside` to let it keep firing.
- **Error** — two handlers catching the same host (or both host-less), trigger, and code (or both catch-all) — the catch would be ambiguous; a coded handler and a catch-all for the same trigger may coexist, and so do two handlers sharing a trigger and code that attach to _different_ hosts, or a host-less handler and a hosted one that otherwise share a trigger and code — each keys a separate engine subscription. For `message` and `signal`, which always carry a name, this is a duplicate-name check instead. `timer` and `condition` handlers are exempt from this check and may repeat freely on one host (or host-less) — the engine keys no subscription name for either, so two timers with different deadlines, or two condition handlers, do not conflict. `compensation` is exempt from that carve-out the other way: since it carries no code to disambiguate by and the engine allows only one compensation event sub-process per subprocess level, a second `on compensation` block in the same subprocess is always a duplicate, with no coexisting catch-all case to permit.
- **Error** — a duplicate binding field in one handler's parameter list, a `message` binding on an `escalation` handler (escalations carry no message text), or a binding variable already declared elsewhere with a non-`string` type.
- **Error** — a host that does not resolve to an activity — a `user`/`service`/`external`/`script` task, a `subprocess`, or a `call` — naming what it actually is instead (a start/end event, a `goto`, a `throw`/`emit`, or another handler are all rejected); an `escalation` host outside the `subprocess`/`call`/`user` set Operaton itself allows; a host that resolves to a step inside the handler's own body (that step only ever runs after this same event has already fired, so attaching to it is circular); or a host at all on `on compensation`, which has no attached form and points the author at the subprocess undo block instead.
- **Error** — a statement named with the reserved `Boundary_` prefix, the synthesized id template a hosted handler's boundary event uses.
- **Error** — a duplicate `error "CODE" message "…"` declaration for the same code, or one with an empty code or message string.
- **Warning** — an empty `on` handler body (zero statements) — the same empty-body warning a process or subprocess gets.

`goto` targets — and a hosted handler's `host` reference — are resolved by a custom `ScopeProvider` (`src/bpmn-script-scope-provider.ts`) that limits both to the steps of their own nearest enclosing _container_ — the `process`, the `subprocess`, or a host-less `on` handler body they directly sit in — at any block-nesting depth within that container. A `goto` can therefore never resolve into another process's steps, into a sibling or nested `subprocess`'s interior, into or out of a host-less `on` handler's body, or out to the parent container from inside one of these, even when both are declared in the same file; a `subprocess` statement is itself a valid `goto` target, resolved from its own container, the same way any other step is (an `on` handler has no name of its own, so it is never itself a target). This mirrors BPMN's rule that a sequence flow cannot cross a sub-process boundary — a host-less event handler being a kind of sub-process, the same rule applies to it: its steps only run once its event fires, so a `goto` cannot pretend otherwise from outside, and the handler's own steps cannot escape back out either. A _hosted_ handler is the one exception: its body is not a container of its own, so the container walk skips straight past it, and a `goto` crosses freely in both directions between a hosted handler's body and the main flow it attaches to — which is also how the handler's `host` reference resolves, against that same surrounding container rather than against the handler's own body. One consequence of that transparency is easy to miss while authoring: a host-less handler written _inside_ a hosted handler's body does not scope to just that escape path — it lowers into, and therefore guards, the whole surrounding container the hosted handler itself attaches to, the same way it would if written directly there. A cross-boundary `goto` (or an out-of-scope `host`) therefore fails to resolve — and a custom `Linker` (`src/bpmn-script-linker.ts`) replaces Langium's generic "could not resolve reference" message with a boundary explanation naming the sub-process or handler the target lives inside or outside of (e.g. `'X' is inside subprocess 'Y'; a goto cannot cross a sub-process boundary.`, across a handler boundary by its header since it has no name of its own — `'X' is inside the 'on error "PAYMENT_FAILED"' handler; a goto cannot cross an event handler boundary: an event handler's steps run only when its event fires.`, or, for an out-of-scope host, `'X' is outside subprocess 'Y'; a boundary event attaches to an activity in its own scope.`) whenever the referenced name exists elsewhere in the process; the generic message is left unchanged when the name exists nowhere at all. Using a reserved keyword where an identifier is expected (e.g. `if (date > deadline)`) is caught by a custom `ParserErrorMessageProvider` (`src/bpmn-script-parser-error-message-provider.ts`), which names the offending word and points to the quoted `"${…}"` raw-expression fallback instead of surfacing Chevrotain's raw token-mismatch message.
